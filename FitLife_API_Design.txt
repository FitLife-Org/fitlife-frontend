1. Tổng quan và quy ước API
1.1. Mục tiêu tài liệu
Tài liệu này là nguồn tham chiếu API thống nhất của FitLife. Mỗi API phải được đối chiếu giữa yêu cầu chức năng, Controller thực tế, Frontend service, kiểm thử và luồng demo. Trạng thái trong tài liệu không thay thế kiểm chứng bằng source code và test evidence.
1.2. Nguyên tắc thiết kế
* RESTful, ưu tiên danh từ số nhiều và endpoint thể hiện rõ phạm vi actor.
* Không nhận memberId từ client đối với API /me; backend resolve từ JWT.
* Các thao tác thay đổi trạng thái phải kiểm tra quyền, ownership, trạng thái hiện tại và tính idempotent.
* API tài chính và callback phải dùng transaction, kiểm tra chữ ký và chống xử lý lặp.
* Không trả entity trực tiếp; sử dụng request/response DTO và ApiResponse chuẩn.
* Xóa dữ liệu nghiệp vụ quan trọng ưu tiên soft delete hoặc chuyển trạng thái.
1.3. Trạng thái API
Trạng thái
	Ý nghĩa
	PLANNED
	Có trong phạm vi nhưng chưa code
	IMPLEMENTED
	Backend đã code
	FE_INTEGRATED
	Frontend đã tích hợp
	TESTED
	Đã test và có evidence
	DEMO_READY
	Đã sẵn sàng cho demo
	NEED_AUDIT
	Chưa đối chiếu controller/source thật
	DEPRECATED
	Không còn sử dụng
	OUT_OF_SCOPE
	Loại khỏi phạm vi bảo vệ
	1.4. Mức ưu tiên
P0
	Bắt buộc cho luồng chính, demo hoặc bảo vệ.
	P1
	Quan trọng nhưng có thể giảm phạm vi nếu thiếu thời gian.
	P2
	Nâng cao; không được chặn P0/P1.
	1.5. Response contract đề xuất
{ "code": 0, "message": "Success", "data": { ... }, "timestamp": "2026-07-30T10:00:00+07:00" }
Với danh sách phân trang, data nên chứa items/content, page, size, totalElements và totalPages. Lỗi phải trả code nghiệp vụ ổn định, message dễ hiểu và fieldErrors khi validation thất bại.

2. Auth API
Mô tả chức năng: Xác thực, phát hành token, xác minh email và khôi phục quyền truy cập tài khoản.
Phạm vi chức năng
Nhóm API này cung cấp các thao tác đọc/ghi phù hợp với actor được chỉ định. Backend phải kiểm tra authentication, authorization, ownership, validation và trạng thái nghiệp vụ trước khi xử lý.
Danh sách API
Mã
	Method
	Endpoint
	Actor
	Priority
	Trạng thái
	Mô tả chức năng
	AUTH-01
	POST
	/auth/register
	Guest
	P0
	Implemented
	Đăng ký tài khoản mới và khởi tạo hồ sơ người dùng.
	AUTH-02
	POST
	/auth/login
	Guest
	P0
	Implemented
	Xác thực thông tin đăng nhập và trả về token cùng quyền truy cập.
	AUTH-03
	GET/POST
	/auth/verify-email
	Guest
	P0
	Need Audit
	Xác minh email bằng token hoặc mã xác thực.
	AUTH-04
	POST
	/auth/resend-verification
	Guest
	P1
	Need Audit
	Gửi lại thông tin xác minh email.
	AUTH-05
	POST
	/auth/forgot-password
	Guest
	P0
	Implemented/Need Audit
	Khởi tạo quy trình quên mật khẩu và gửi OTP/token.
	AUTH-06
	POST
	/auth/reset-password
	Guest
	P0
	Implemented/Need Audit
	Đặt mật khẩu mới sau khi xác thực OTP/token.
	AUTH-07
	POST
	/auth/refresh-token
	Authenticated
	P1
	Need Audit
	Cấp access token mới từ refresh token hợp lệ.
	AUTH-08
	POST
	/auth/logout
	Authenticated
	P1
	Need Audit
	Kết thúc phiên đăng nhập hoặc vô hiệu hóa refresh token.
	AUTH-09
	GET
	/oauth2/authorization/google
	Guest
	P1
	Need Audit
	Lấy danh sách dữ liệu theo quyền truy cập và bộ lọc hỗ trợ.
	AUTH-10
	GET
	/auth/check-email
	Guest
	P1
	Frontend flow
	Kiểm tra email đã tồn tại hoặc có thể đăng ký.
	Quy tắc và điểm cần kiểm tra
* Đối chiếu URL thật của controller.
* Chốt verify email dùng GET hay POST.
* Xác nhận refresh token và logout có trong scope.
* Chốt Google Login có giữ trong phiên bản bảo vệ.
* Kiểm tra ErrorCode cho LOCKED/INACTIVE và quy tắc emailVerified.
Điều kiện hoàn thành nhóm API
Các API P0 của module chỉ được xem là hoàn thành khi Backend implemented, Frontend tích hợp nếu có màn hình, QA test cả success/failure, Swagger cập nhật và luồng demo không còn blocker mức High/Critical.

	24. Definition of Done của một API
* URL và HTTP method khớp Controller.
* Mô tả chức năng và contract được chốt.
* Request validation đúng.
* Response DTO và HTTP status đúng.
* Authentication/authorization/ownership đúng.
* ErrorCode rõ ràng và ổn định.
* Transaction và idempotency đúng với API ghi dữ liệu.
* Frontend tích hợp nếu thuộc màn hình.
* Success case và failure case đã pass.
* Không còn lỗi High/Critical.
* Swagger/OpenAPI cập nhật.
* Có dữ liệu và evidence demo.
25. Phụ lục: Quy ước Request/Response/Error
25.1. HTTP status
200 OK
	Đọc/cập nhật thành công.
	201 Created
	Tạo tài nguyên thành công.
	204 No Content
	Xóa hoặc thao tác không cần body.
	400 Bad Request
	Request hoặc validation không hợp lệ.
	401 Unauthorized
	Thiếu hoặc token không hợp lệ.
	403 Forbidden
	Không đủ quyền hoặc ownership.
	404 Not Found
	Không tìm thấy tài nguyên.
	409 Conflict
	Xung đột trạng thái, dữ liệu trùng hoặc callback đã xử lý.
	422 Unprocessable Entity
	Dữ liệu hợp lệ cú pháp nhưng vi phạm business rule.
	500 Internal Server Error
	Lỗi hệ thống chưa xử lý.
	25.2. Pagination và filter
Các API danh sách nên thống nhất page bắt đầu từ 0 hoặc 1, size có giới hạn, sort theo cú pháp field,direction và filter được mô tả rõ. Mặc định không trả bản ghi soft-deleted.
25.3. Bảo mật
* Không ghi access token, refresh token, API key hoặc dữ liệu nhạy cảm vào log.
* Các API admin/staff/trainer phải kiểm tra role ở SecurityConfig và/hoặc method security.
* API /me luôn resolve người dùng từ SecurityContext.
* Callback VNPay kiểm tra signature, amount, transaction reference và idempotency.
